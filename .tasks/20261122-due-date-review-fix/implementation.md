### Spec

- 足りない要件：なし（Q1〜Q14 はすべて実装済み、カバレッジも依頼どおり）。テストのすき間は、storage 側に「正しくない期限日を含む v2 データ」のテストがないことと、日付が変わった直後（0:00）のテストがないこと。
- 頼まれていない変更：`backupFileName` を `toDateString` を使う形に変えたことと、時刻付きの値をエラーにしたことの2つ。どちらも小さく、後者は前回の requirements.md に記載されている。
- 問題：日付欄の値を確かめずに保存していた。読み込むときの `isDateString` は、5桁以上の年（Chrome の日付欄は 275760 年まで入れられる）と 0001〜0099 年の日付をはじく。そのため、そうした日付を1件でも保存すると、開き直したときに一覧全体が空になり、次の操作で空の一覧が保存される。
  - 0001〜0099 年がはじかれるのは、`Date.UTC` が 0〜99 年を 1900 年代として扱うため。`Date.UTC(50, 0, 1)` が 1950 年になることを Node で確かめた。

## 4. 修正を TDD で行う

- ユーザーの「直して」を受けて、Spec 軸の問題を直した。
- 先にテストを書き、App の2本と backup の「0050年を読み込める」の3本が失敗することを確かめた。
  - App：5桁の年は、追加フォームと一覧のどちらの日付欄でも受け付けず、開き直してもタスクが残る
  - App：0050年の期限日を指定でき、開き直しても残る
  - backup：0050年の期限日を含むファイルを読み込める
  - backup：5桁の年を含むファイルはエラーになる（今の実装でも通る）
  - storage：正しくない期限日を含む保存データなら空の一覧を返す（テストのすき間を埋めた。今の実装でも通る）
- 実装：
  - `isDateString` を `todoData.ts` から `todo.ts` に移して export した（書き込み側からも使うため）。年は `Date.UTC` ではなく `setUTCFullYear` で設定するようにした。
  - `todo.ts` に `parseDueDateInput` を足した。空なら `null`、正しい日付ならその値、保存できない値なら `undefined` を返す。
  - `App.tsx` では、追加フォームの日付欄を `changeDraftDueDate` で、一覧の日付欄を `changeDueDate` で受け、`undefined` なら何もしないようにした。日付欄は制御された input なので、受け付けなかった値は元に戻る。追加するときの変換も `parseDueDateInput` を使うようにし、Standards 指摘1の `'' ? null :` の重複がなくなった。
  - [docs/spec.md](../../docs/spec.md) の「期限日」に、年が4桁でない日付は受け付けないことと、その理由を書いた。テスト方針の表にも追記した。

### Claude が決めた点

- 受け付けない値は、エラー表示を出さずに無視し、日付欄を元の値に戻すことにした。日付欄で5桁の年を入れるのは、ほぼ入力ミスと考えたため。
- 0001〜0099年は正しい日付として通すことにした（はじくのではなく、読み込み側を直した）。
- 日付欄に `max="9999-12-31"` を付けることはしなかった。
- Standards のほかの指摘（日付をただの文字列で扱っている点、版番号の直書きなど）は、判断の余地があるものなので、手を入れなかった。
